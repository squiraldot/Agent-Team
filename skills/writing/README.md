# Writing Skill

## Procedure

1. Identify reader, purpose, format, language, expertise level, and next action.
2. Lead with the main answer, decision, or outcome.
3. Organize information with headings that communicate conclusions.
4. Prefer concrete examples, active voice, and specific verbs.
5. Define unfamiliar terms and explain assumptions.
6. Keep factual claims proportional to evidence; cite research and label uncertainty.
7. Remove repetition, filler, unsupported superlatives, and misleading certainty.
8. Make lists parallel and tables readable; use code blocks for literal commands/data.
9. Review accessibility, inclusive language, localization, and copy/paste usability.
10. Check every link, filename, command, version number, and placeholder.
11. Match tone to the audience without hiding important caveats.

## Technical documentation checklist

- Is the intended user and prerequisite level clear?
- Does the first successful path work from a clean setup?
- Are examples safe, complete, and clearly marked if illustrative?
- Are expected outputs and failure modes described?
- Are security, privacy, permissions, and cost implications covered?
- Are commands tested where possible and test status reported accurately?
- Are compatibility limitations and version-specific behavior explicit?
- Can the reader recover from an error or undo a change?

## Email, public copy, and external messages

Draft first. Do not send, publish, schedule, or contact anyone without explicit authorization. Avoid fabricated urgency, false claims, fake testimonials, or undisclosed sponsorship.

## Final review

Read once for factual correctness, once for structure/readability, and once for safety and missing requirements. Keep the final artifact self-contained enough to be useful without hidden conversation context.
