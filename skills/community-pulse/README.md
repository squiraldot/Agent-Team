# Community Pulse Skill
Find recurring pain points, complaints, feature requests and workarounds in public communities to generate hypotheses—not consensus or profiles.

1. Define product, versions, time window, languages, communities and decision; avoid confirmation-seeking.
2. Use permitted public sources from research/sources.md. Respect terms, robots.txt, rate limits, copyright, community rules and API limits. Never scrape private/paywalled/login-gated/invite-only/restricted content.
3. Search neutrally for problems, failures, workarounds, requests, regressions and alternate explanations across multiple communities.
4. Capture paraphrase, URL, post/access dates, version, tier, symptom and evidence quality. Do not collect handles, profiles, emails or demographics.
5. Deduplicate reposts/cross-posts; group by symptom, workflow, environment and version.
6. One post is an anecdote. Look for independent reports, distinct environments, dates, reproduction, maintainer acknowledgement and tracker evidence. Votes/likes show engagement, not prevalence.
7. Cross-check with official docs, changelogs, maintainers or reproducible tests; record counter-evidence, alternate causes, fixes and issue closure reasons.
8. Label **anecdote**, **emerging signal**, **repeated pattern** or **corroborated issue** (pattern plus maintainer/official evidence or reproduction). Never estimate prevalence without a defensible sampling frame/denominator.
9. Recommend reproduction, user research, support content or a scoped fix, with confidence and bias.

Independent reports across sources outweigh replies in one viral thread. Verify workarounds for safety/policy; closed issues may be duplicates or fixed. Paraphrase and attribute; remove identifiers; never expose private content. Output method, limits, themes, anonymized paraphrases/source links, defensible counts, counter-evidence, confidence and next steps.
